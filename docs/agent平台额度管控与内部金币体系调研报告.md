## 0. 执行摘要

本报告在贵方既有草案基础上，用 2026-07 真实数据校验并重算，补齐了工程层与内部结算架构。**关键前提已据贵方澄清锁定**：

- **金币是既有内部体系**（已运行很久，可兑换奖品等其他权益），**10 金币 = 1 元的比例固定不可动**。本报告不再讨论调整比例，只在「其他可优化处」做文章。
- **消耗金币一律四舍五入取整**，不追求小数精度。
- **抵扣优先级**：优先消耗「每日赠送额度」；「金币兑换 token」作为后续阶段能力，**MVP 不做**。
- **MVP 限额只做到用户个人层级**（每日 + 月度）；企业 / 部门 / 项目分层与共享池为后续阶段。

**六个核心结论：**

1. 行业普遍用「积分 / Credits」作为统一计量抽象层，兑换比例集中在 **0.01–0.05 元/积分**，并锚定现金（Coze 1000:1[^coze]、腾讯云 100:1[^tencent-internal]、MS Copilot Studio $200=25,000 Credits[^mscopilot]、GitLab $1/Credit[^gitlab]）。你们的「金币」思路同构，且 10:1 已是现成体系，直接接入即可。
2. 三级配额（企业→部门→个人）+ 共享池 + 个人独占配额是行业事实标准（Coze 企业版共享积分池[^coze]、腾讯云 Token Plan 同套餐 Key 共享池+独占配额[^tencent-internal]、百炼坐席额度+共享包[^bailian]）。
3. 超额三模式：自动扣款续费（Coze[^coze]）、拦截消耗（阿里云 STAROps[^tencent-internal]）、等待重置（月度额度[^tencent-internal]）。预警普遍设 70% / 90% / 100%。
4. 工程层靠「令牌桶 + 多时间窗 + 成本熔断」：秒级防 DDoS、分钟级防滥用、日/月级防资源吸血；429 响应带回 `Retry-After`、限流头、成本头[^eng]。

**三张红牌（硬约束）：**

- 🔴 **百炼 Token Plan 团队版条款限制**：白纸黑字「仅限在兼容的 AI 编程和智能体工具中**交互式使用，不可用于自动化脚本或应用后端**」[^bailian]。你们是后端多租户 Agent 平台，直接调用会违反 ToS、有封禁风险。**必须改用百炼「按量付费 / 资源包 / 节省计划」接入，不要用 Token Plan 坐席。**
- 🔴 **DeepSeek V4 峰谷定价**：高峰时段（每日 9:00–12:00、14:00–18:00，北京时间）价格 **×2**[^deepseek-peak]。金币若按固定比例锚定人民币，峰时底层成本翻倍会直接吃掉毛利。建议按「高峰价」锚定或预留 30% 缓冲。
- 🔴 **草案的成本估算偏高 3–7 倍**：草案按原价/旧价估算（如标准任务 0.02–0.04 元），而 DeepSeek V4 Pro 当前为**永久 2.5 折**（输入 3 元 / 输出 6 元每百万 token）[^deepseek-price]，标准任务真实成本约 **0.006 元**。本报告已用真实单价重算（见 §4.2）。

### 2.2 三级配额体系（企业 → 部门 → 个人）

- **腾讯云 ClawPro**[^tencent-internal]：企业级总控（全局 Token 上限 + Agent 总数兜底）→ 部门级资源池切分 → 个人级精细限制，呈「漏斗型」。
- **扣子企业版**[^coze]：可按企业成员/角色、工作空间、组织、设备/自定义实体设置用量限额；企业成员**共享企业版积分池**。
- **OpenAI API**[^openai]：6 个账号层级（Free + Tier1–5），层级由累计消费决定，对应不同的速率与用量上限——「账号层级→配额」的另一种落地。
- **OpenAI ChatGPT Enterprise**[^openai]：支持在工作区、群组、个人用户层灵活配置月度积分限额。

> **MVP 范围约定**：三级配额是行业共识，但 **MVP 先只做「个人层级」**（每人的每日 + 月度上限）。企业/部门/项目分层与共享池列入后续阶段（见 §6）。

### 2.3 配额类型

- **累计额度**：从开始使用到当前的总量上限。
- **周期额度**：按月/按日重置（行业以「月」为主）。
- 两者常组合使用（月度总池 + 日度护栏）。MVP 建议至少落地「每日额度」（核心护栏）+ 可选的「月度累计上限」。

### 2.4 超额处理三模式

| 模式 | 代表 | 做法 | 来源 |
|------|------|------|------|
| 自动扣款续费 | 扣子企业版 | 积分不足按 1000:1 从现金账户自动扣款 | [^coze] |
| 拦截消耗 | 阿里云 STAROps | 达上限自动拦截消耗积分的操作 | [^tencent-internal] |
| 等待重置 | 阿里云 Hermes Agent | 月度用完后等待下月重置或订阅积分包 | [^tencent-internal] |

> **MVP 范围约定**：MVP 不做「金币兑换 token 续费」。每日额度用尽即**拦截/提示**（可提示「今日额度已用完，明日重置」），是否开放「用金币余额兑换更多 token」留待后续阶段（见 §4.3、§6）。

### 2.5 资源池模式：共享池 + 个人独占配额

- **扣子企业版**[^coze]：企业成员共享企业版积分（共享池），席位增购即增购订阅积分。
- **腾讯云 Token Plan**[^tencent-internal]：同一套餐下所有 API Key 共享积分池，可为每个 Key 设**独占配额**与**配额上限**。
- **GitLab Credits**[^gitlab]：组织范围池化，自动抵消重度/轻度用户差异。
- **百度千帆**[^draft]：席位制 + 企业共享积分包。

> **MVP 范围约定**：共享池/独占配额为后续阶段能力，MVP 仅「个人独立额度」。

### 2.6 消耗计量：差异化扣减

- **按任务复杂度**（Warp）：任何交互至少 1 个 Credit，复杂交互按 LLM 模型、工具调用次数、任务复杂度、上下文量差异化[^warp]。
- **按模型类型**（百炼 Token Plan）：不同算力等级模型设固定 Credits 扣减比例，无需区分输入输出单独核算[^bailian]。
- **按成果定价（新兴）**：LTM BlueVerse Currency 按业务成果而非资源消耗计费，含固定+可变混合结构[^draft]——值得在体系里预留接口。

## 3. 工程层：配额 / 限速 / 成本熔断怎么做[^eng]

行业成熟的配额系统不是「设个数就完事」，而是**令牌桶算法 + 多时间窗 + 成本熔断**的组合。

### 3.1 令牌桶 + 多时间窗防御体系[^eng]

| 窗口 | 目的 | 典型配置 |
|------|------|---------|
| 秒级（1–60s） | 防 DDoS / 突发流量 | 令牌桶 `burst_capacity=5, refill_rate=1/s`（高成本模型） |
| 分钟级（1–60min） | 防常规滥用 | `rolling_window=300, max_requests=500` |
| 长周期（日/月） | 防「资源吸血鬼」长期占用 | 日/月硬顶；电商预留促销弹性、教育放宽学期初末 |

> 反例：某社交平台只设日配额，凌晨遭爬虫榨干，单日 API 费用损失 $15k[^eng]。

### 3.2 模型档位分级限速[^eng]

| 模型档 | 策略 |
|-------|------|
| GPT-4 级（贵） | 阶梯递减配额 + token/s 限制，企业版可购突发额度 |
| Claude 级 | 并发数限制 + 请求延迟监控，启用智能降级 |
| 国产/开源级（便宜） | 时长限制 + GPU 利用率监控，开放批量请求 |

### 3.3 429 响应透明化设计（最佳实践）[^eng]

完整 429 应包含五层信息，让调用方和财务都看得见：

```
HTTP/1.1 429 Too Many Requests
Retry-After: 63
X-RateLimit-Limit: 100
X-RateLimit-Used: 78
X-RateLimit-Reset: 3600
X-Cost-Limit: $1.00
X-Cost-Used: $0.42
X-Cost-Per-Request: $0.005
X-Upgrade-Url: https://api.example.com/plans
X-Diagnostic-Code: RATE_LIMIT_03
```

### 3.4 成本熔断与硬顶[^eng]

| 维度 | 公式 | 硬顶示例 |
|------|------|---------|
| 单次请求 | `base_cost + tokens×price` | $0.10 / req |
| 每分钟 | `sum(requests_cost)` | $1.00 / min |
| 每日 | `cumulative_cost` | $50.00 / day |

触发：`daily_cost > quota × 1.2` → 熔断冷却 + 通知财务。

### 3.5 滥用检测[^eng]

- **流量指纹**：同一 API Key 1 小时内出现在 3+ 国家触发告警；傅里叶变换识别周期性攻击。
- **沙箱行为监控**：定义危险工具链（如 `file.read → http.post`、`db.query → email.send`），建立用户行为基线做异常打分。

## 4. 内部金币（虚拟积分）结算模型建议

> 前提锁定：**金币为既有内部体系，10 金币 = 1 元固定不可动；消耗金币四舍五入取整；抵扣优先用每日赠送额度；金币兑换 token 为后续阶段、MVP 不做。**

### 4.1 兑换比例：固定 10:1（不可动）

10 金币 = 1 元是贵方已运行很久的内部体系（还可兑换奖品等权益），**比例不动**。本报告不讨论改比例，优化空间在「计量精度、抵扣顺序、限额层级、峰谷对冲」等处。

> 行业对比仅供参考（不要求对齐）：Coze 1000:1[^coze]、腾讯云 100:1[^tencent-internal]、MS Copilot $200=25,000 Credits（≈0.008 美元/Credit）[^mscopilot]、GitLab $1/Credit[^gitlab]。你们的 0.1 元/金币面额偏大，但既有体系优先，无需调整。

### 4.2 金币消耗锚定真实成本 + 四舍五入取整

**关键修正**：草案任务分级的「人民币成本」偏高 3–7 倍（用的是原价/旧价）。以下用 **DeepSeek V4 Pro 平时价（3/6 元每百万，永久 2.5 折）**[^deepseek-price] 为锚点重算，并以 **10 金币 = 1 元** 折算金币：

| 任务等级 | Token 量级 | 真实成本（V4 Pro 平时） | **消耗金币（原始值）** | **四舍五入后（扣减值）** |
|---------|-----------|------------------------|---------------------|------------------------|
| 微型（意图识别/抽取） | ~200 | ~¥0.0008 | 0.008 | **0.1**（设单次最低 0.1） |
| 小型（一句话问答） | ~750 | ~¥0.003 | 0.03 | **0.1** |
| 标准（普通问答/润色） | ~1,500 | ~¥0.006 | 0.06 | **0.1** |
| 增强（写邮件/小方案） | ~4,000 | ~¥0.015 | 0.15 | **0.2**（四舍五入） |
| 复杂（10 页文档/RAG） | ~12,000 | ~¥0.048 | 0.48 | **0.5**（四舍五入） |

**四舍五入规则（推荐）**：
- 单次消耗先按「实际 token × 模型实时单价（感知峰谷）× 难度/工具乘数」算出原始金币数。
- 再 **四舍五入保留 1 位小数**；并设 **单次最低扣除 0.1 金币**，避免微任务被舍成 0、变相免费。
- 四舍五入（0.5 进位）在统计上略偏「多扣」，对成本管控是保守安全的；与「10:1 不可动」的约束完全兼容，不必追小数精度。

> ⚠️ **但 Agent 任务不等于单次对话**。带工具调用、多轮、RAG 的 Agent 任务可达普通对话的 **10–1000 倍**（单 Agent 企业级场景平均约 90 次工具调用、100 万 token；智能体工作流可达 60 万 token）。这类任务真实成本几十到上百元，**单任务可能消耗数百金币**。

**因此扣减模型建议（重要）**：

> **不要用「固定任务系数」脱离真实成本去扣金币。** 正确做法是：
> `金币消耗 = 实际 Token 用量 × 该模型实时单价（感知峰谷）× 难度/工具乘数（Agent 任务 3–20×）`
> 算出原始值后**四舍五入取整（1 位小数，最低 0.1）**，并设 **单任务硬上限（建议 500 金币）** 兜底，超出提示「任务过于复杂，请联系管理员」。

这样金币体系既能精确对齐底层成本（避免通胀/贬值），又用乘数体现 Agent 的额外开销，且扣减是整数化、可解释的。

### 4.3 抵扣优先级：每日赠送额度优先，金币兑换为后续

| 阶段 | 抵扣来源 | 说明 |
|------|---------|------|
| **MVP** | ① 每日赠送额度（优先，当日有效） | 仅此一项。用尽即拦截/提示「今日额度已用完，明日重置」 |
| **后续阶段** | ① 每日赠送额度 → ② 金币余额兑换 token → ③ 团队共享池 | 参考百炼「坐席额度→共享包→暂停」同构逻辑[^bailian] |

> **MVP 明确不做「金币兑换 token」**。但接口与记账要预留：每日额度耗尽后，未来可允许用户以 **10 金币 = 1 元** 的固定比例，用既有金币余额兑换 Agent 额度继续任务（优先级在每日赠送额度之后）。

### 4.4 MVP 限额：仅到用户个人层级

| 层级 | MVP 是否做 | 管控内容 | 参考 |
|------|-----------|---------|------|
| **个人（MVP 必做）** | ✅ | 每人每日额度 + 可选月度累计上限 | 个人日/月配额[^tencent-internal][^coze] |
| 部门/项目 | ❌ 后续 | 按部门/项目分配独立金币池 | 扣子空间/组织维度[^coze] |
| 企业总池 | ❌ 后续 | 月度总金币上限，全局兜底 | 腾讯云 ClawPro 企业级总控[^tencent-internal] |

**MVP 个人限额建议参数**：
- 每日赠送额度：**50 金币当量/人/日**（= ¥5/人/日，当日有效，次日清零）。在真实 DeepSeek 单价下，足够支撑大量日常对话；重度 Agent 任务会快速耗尽，正好起「体验充足 + 成本可控」的平衡。
- 可选月度累计上限：防个别用户月初狂刷（如月度 1500 金币当量 = ¥150/人/月）。
- **优先级规则**：个人任一额度（每日或月度）达上限即阻止消耗。

### 4.5 预警与超额机制（MVP 精简版）

| 阈值 | 触发动作 | 参考 |
|------|---------|------|
| 日额度 70% | 推送「今日额度已用 70%，剩余 XX 金币」 | Cursor 支出预警思路[^draft] |
| 日额度 100% | 拦截/通知「今日额度已用完，明日重置」 | 阿里云 STAROps 拦截[^tencent-internal] |

> 月度 80%/100% 管理员预警、超额审批流为后续阶段（配合企业/部门分层上线）。

### 4.6 数据看板与审计（MVP 至少做个人维度）

- **个人维度（MVP）**：每人每日/每月消耗、剩余额度、消耗趋势、每笔消耗明细（时间、操作人、任务类型、金币变动、余额、说明）。
- **部门/企业维度（后续）**：部门总消耗、人均消耗、Top 消耗用户、成本分账（按组织/工作空间归属费用，支持「项目 + 资源用量 + 业务贡献」分摊[^settle]）。

## 5. 针对你们平台的落地建议（我们应该怎么做）

### 5.1 供应商与合规（选型红线）
- **DeepSeek V4**：作为性价比锚点，注意峰谷定价。
- **阿里百炼**：**后端调用必须走「按量付费 / 资源包 / 节省计划」，严禁用 Token Plan 团队版坐席**（ToS 禁止后端自动化）[^bailian]。百炼同样统一账户结算、数据不出境、有 SLA，是合规优选。
- **腾讯云 TokenHub**：若体系内，7 月中旬上线的 DeepSeek-V4 原厂直供是可统一结算的备选[^tokenhub]。
- 建议做**统一接入网关**，把 DeepSeek / 百炼 / 未来模型都收敛到一套「内部金币抽象 + 统一结算」，屏蔽供应商差异。

### 5.2 峰谷定价对冲
- 金币锚定建议**按 DeepSeek 高峰价（输入 6 / 输出 12 元每百万）保守折算**，或平时价折算后**预留 ≥30% 缓冲**，避免峰时毛利被吃[^deepseek-peak]。
- 或在产品层做「闲时激励」：非高峰时段金币消耗打 8 折，引导负载均衡。

### 5.3 内部结算中枢架构（参考 Taotoken 思路）[^settle]
构建「模型资源池化 → 接入标准化 → 成本可视化 → 按项目分摊」的中枢：
1. 所有业务团队通过统一 SDK/网关调用，不直接持供应商 Key。
2. 网关做计量（token、工具调用、模型档位）→ 实时换算金币（四舍五入）→ 写 consumption ledger。
3. 财务侧按「部门/项目/个人」出账单，对接内部结算。

### 5.4 多模型统一金币抽象
- 内部只流通「金币」一种单位，底层 DeepSeek/百炼/未来模型的真实价差由网关折算层吸收。
- 模型升级（如从 Flash 切 Pro）对用户只体现为金币扣减变多，不暴露复杂计价。

### 5.5 单任务上限 + 预估提示
- 单任务硬上限（建议 500 金币），超限拦截。
- 任务发起前**显式预估金币消耗**（参考 §3.3 的成本透明头），避免「不知不觉烧光」。

### 5.6 给产品/财务的 MVP 起步参数建议
- **比例**：10 金币 = 1 元（**固定，既有体系，不可动**）。
- **每日赠送**：50 金币当量/人/日（=¥5/人/日 ≈ ¥150/人/月）。
- **扣减**：实际 token × 实时单价（感知峰谷）× 难度乘数 → **四舍五入保留 1 位小数，单次最低 0.1 金币**。
- **单任务上限**：500 金币。
- **MVP 限额层级**：仅个人（每日 + 可选月度）。
- **预算缓冲**：预留 20–30% 应对突发。

## 7. 风险与合规

1. **🔴 百炼 ToS 红线**：后端自动化不可用 Token Plan，务必走按量付费/资源包[^bailian]。
2. **🔴 峰谷定价**：固定金币锚定需按高峰价或加缓冲，否则峰时净成本翻倍吃掉毛利[^deepseek-peak]。
3. **金币通胀**：严格锚定既有 10:1 现金成本，不随意增发；AI 模型成本波动快，**每季度复核一次**换算比例。
4. **合规属性**：明确金币是「虚拟记账单位」（且已是既有内部权益体系），避免被认定为具有货币属性引发合规风险。
5. **预留弹性**：预算预留 20–30% 缓冲。
6. **向成果定价演进**：体系预留接口，未来可部分转向「按业务成果」计费（参考 LTM BlueVerse）[^draft]。
