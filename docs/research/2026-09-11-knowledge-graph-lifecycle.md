# 企业知识图谱可行性与生命周期调研

## 一、研究结论

企业知识图谱具备可行性，但不建议直接作为 V1.1.0 正式功能上线。建议在 V1.2 做小范围验证，在实体关系质量、成本、权限和增量更新均通过门槛后，再评估 V1.3 产品化。

推荐采用“现有知识中心为事实来源，图谱作为派生索引”的方案：

    原始知识来源
      → 现有解析、切片与 RAG
      → 图谱抽取任务
      → 文档、实体、关系和来源证据
      → 图谱展示与 GraphRAG 检索

图谱不能取代原始文档、向量索引和权限系统。任何实体和关系都必须能追溯到有效来源。

## 二、为什么图谱不会自动更新

Microsoft GraphRAG 将建图定义为索引管线，包含实体、关系、声明、社区和向量等处理，并提供独立的 update 命令。更新结果默认写入 update_output，说明更新是一个需要显式发起、监控和切换的过程。[^1][^2]

Microsoft 的增量索引代码会读取上一次文档表，与当前输入按文档标题比较，计算新增和删除集合。[^3] 这证明“发现变化”本身也是应用任务，不是图数据库自动完成。

Neo4j 的官方 GraphRAG 构建器包含加载、切分、向量化、模式、实体关系抽取、写入和实体消歧等步骤。[^4] 图数据库只负责存储和查询，不会主动回到知识库读取修改后的 Excel 或 PDF。

结论：

- 数据源负责告诉天马“来源可能变化了”。
- 天马同步器负责判断新增、修改、删除和失权。
- 图谱任务负责对新增或修改内容重新抽取。
- 图数据库负责幂等写入、版本切换、查询和来源追溯。

## 三、如何判断内容变化，而不先做完整解析

“知道文件有什么内容时，不就已经在解析了吗”需要区分两个动作。

### 变化检测

变化检测只回答“这份来源和上次是否一样”，不理解业务语义。优先使用：

1. 外部系统提供的版本号或修订号；
2. 修改时间加文件大小；
3. 外部系统提供的内容摘要；
4. 如果以上都没有，下载原文件计算内容哈希。

下载文件并计算哈希不等于执行 LLM 实体关系抽取，成本和耗时远低于图谱解析。

### 语义抽取

只有检测到新增或内容哈希变化后，才执行文档解析、实体识别、关系提取、置信度判断和图谱写入。

### 删除判断

删除不需要读取内容。每次同步取得当前来源 ID 集合，与上次有效来源集合比较；上次存在、本次不存在的来源进入删除确认。对事件明确通知的删除，可立即处理。

### 权限变化判断

优先使用权限变更事件；没有事件时定期读取来源权限摘要或允许访问的对象集合。权限撤销不需要重新抽取内容，而是立即调整来源有效性和用户可见范围。

## 四、方案比较

### 方案 A：在现有知识中心上增加图谱派生层

做法：现有知识资产、解析结果和权限继续作为主数据，新增图谱抽取、图数据库和展示。

优点：

- 与现有 RAG 和知识权限一致；
- 删除、失权和重试可以复用知识来源状态；
- 容易保留文档、段落和关系证据；
- 可以逐步上线，不要求一次替换现有检索。

缺点：

- 需要自建同步、版本、审核和失效治理；
- 图谱与向量索引的一致性需要专门管理。

结论：推荐。

### 方案 B：以 Microsoft GraphRAG 批处理结果为主

优点：

- 具备成熟的全局/局部图检索思想；
- 支持标准和快速索引方法以及 update 命令；
- 适合做跨文档主题、社区和全局问题分析。

缺点：

- 更偏批处理索引和查询框架；
- 更新结果需要额外管理和切换；
- 企业文件级权限、多来源失效和人工审核仍需天马自建；
- 官方提示 GraphRAG 索引可能消耗较多模型资源。[^5]

结论：适合作为抽取和检索参考，不建议直接承担全部产品生命周期。

### 方案 C：使用 Neo4j GraphRAG 构建和存储

优点：

- 文档、分块、实体、关系和来源可以显式建模；
- 适合关系查询和可视化；
- 官方构建器支持模式约束、结构化输出、写入和实体消歧。

缺点：

- 官方知识图谱构建器仍标注为实验能力，升级可能有 API 变化；
- 默认实体消歧可能错误合并同名对象；
- 某个分块抽取失败时，默认行为可能跳过该分块，需要显式改为整体失败或记录不完整。[^4]

结论：适合作为 V1.2 候选技术验证，但天马必须掌握任务和来源生命周期，不能把治理交给库的默认行为。

## 五、推荐产品结构

### 5.1 查看入口

- 单文件：知识文件行内“查看图谱”。
- 文件夹：查看该文件夹内有效来源形成的图谱。
- 知识库：默认范围，查看整库关系。
- 空间：聚合空间内多个知识库。
- 全局图谱：后续入口，用于有权限范围内的跨库查看。

目录层级节点默认隐藏。用户可开启“显示文件夹/知识库/空间”，用于理解来源范围。

### 5.2 图谱主体

主要节点：

- 文档；
- 业务实体，例如人、组织、品牌、产品、部门、指标和业务术语。

主要关系：

- 文档提及实体；
- 实体之间的业务关系；
- 实体或关系来自哪些文档片段；
- 文件属于哪个文件夹、知识库和空间。

文件夹、知识库和空间是范围与来源节点，不应默认占满图谱画面。

### 5.3 图谱治理

技术管理员配置：

- 允许抽取的实体类型；
- 允许抽取的关系类型；
- 不同类型的置信度规则；
- 哪些关系必须人工审核；
- 单次抽取规模；
- 自动重试和手动重试；
- 目录节点默认是否显示。

阈值不在产品需求中固定为 0.8 或 0.5。不同关系风险不同，例如“任职于”和“涉嫌违规”不能使用相同自动入库规则。

## 六、完整生命周期

### 新增

    新来源进入知识中心
      → 知识解析成功
      → 创建图谱抽取任务
      → 实体和关系附带来源证据
      → 达到自动入库规则则生效
      → 需要审核的进入审核队列

知识库上传完成后立即异步抽取，不等待每日任务。

### 修改

    检测到来源修订号或内容哈希变化
      → 旧图谱标记“可能已过期”
      → 新版本抽取
      → 成功后原子切换
      → 旧版本失效但保留审计

新抽取失败时，旧结果暂时仍可查看，但必须明确标记可能过期。

### 删除

    来源删除
      → 来源立即失效
      → 该来源的实体和关系证据立即停止参与展示与检索
      → 不物理删除历史记录

### 权限取消

    来源或用户权限撤销
      → 立即更新可见范围
      → 用户不再看到相关文档、实体、关系和问答结果
      → 不等待下一次图谱抽取

### 多来源

一个关系可以有多个来源证据。单个来源失效时只失效该证据；只要仍有其他有效且有权限的来源，关系可以继续显示。

### 失败重试

初次失败后自动重试 2 次。三次均失败后显示失败原因和手动重试。修改抽取失败保留旧图并标记过期；新增抽取失败不产生半成品图；删除和失权立即排除，不受重试影响。

## 七、幂等和稳定标识

Neo4j 官方说明 MERGE 会在完全匹配时复用、未匹配时创建，但并发场景只靠 MERGE 不能保证节点唯一，必须配合唯一性或键约束。[^6]

产品层应要求以下稳定关系：

- 一个外部来源在天马有稳定来源 ID；
- 同一来源的每次修改有独立修订 ID；
- 实体和关系使用规范化业务标识；
- 实体与来源证据分开，不能把一个实体直接绑定成只有一个来源；
- 重复收到同一同步事件不会重复创建图谱内容。

## 八、权限与失效

推荐采用“查询时权限过滤 + 来源失效”双层保护：

1. 来源层记录当前是否有效。
2. 来源证据记录哪些用户或组织范围可见。
3. 图谱查询只返回至少有一个有效、且当前用户有权限的来源证据的实体和关系。
4. 问答检索和图谱展示使用相同过滤规则。

不能只在前端隐藏节点，也不能只在首次抽取时复制一次权限后永久不更新。

## 九、内部参考平台观察

内部参考页面已展示：

- 知识抽取规则与“本次上传临时使用其他规则”；
- 个人、公共、共享空间；
- 单文件“查看图谱”；
- 全局图谱入口；
- 抽取进度；
- 成功、抽取中和失败状态；
- 失败后的 Saga 回滚补偿提示；
- 独立“图谱治理”入口。[^7]

这些能力说明参考方向较完整，建议吸收“文件入口、全局入口、规则、进度、失败”五个部分。

不能直接照搬的点：

- 参考页面出现较多 Excel 抽取失败，说明复杂表格的图谱质量要单独验证；
- 回滚提示偏技术化，天马面向管理员应显示可理解原因和下一步操作；
- 参考页面共享空间不包含文件夹，这是其当前限制，不应成为天马的产品规则；
- 仍需补齐修改过期、删除失效、权限撤销、多来源证据和人工审核闭环。

## 十、V1.2 验证范围

样本：

- 50–200 份脱敏文档；
- 同时包含 PDF、普通 Excel 和经营月报；
- 选择 3–5 种核心实体和 3–5 种核心关系；
- 制造新增、修改、删除、失权和多来源案例。

必须验证：

- 实体准确率和关系准确率；
- 同名实体是否被错误合并；
- 来源能否追到具体文档片段；
- 修改后旧图和新图能否正确切换；
- 删除和失权能否立即排除；
- 自动重试和手动重试；
- 单文档抽取成本、总耗时和查询性能。

## 十一、投入与版本建议

| 范围 | 估算 |
|---|---:|
| 技术与产品验证 | 15–25 人日 |
| 文件/知识库两级产品化 | 35–55 人日 |
| 加入文件夹、空间、全局图谱、治理审核 | 50–80 人日 |

建议：

- V1.1.0：不开发。
- V1.2：验证方案和生命周期。
- V1.3：满足准确率、成本、权限和更新门槛后，先上线文件与知识库图谱，再扩展到空间和全局图谱。
